# First mission engine investigation

The Pit is the first target. Its installed zone is so_killspree_trainer.ff. A timed target course gives testers a visible shared start, target state and finish. Spawn, restart and completion script ownership still require verification.

On the supported retail image, the scan at RVA 0x22ed40 tests the leading signed dword against 2, advances by 0x1678 and stops at the address immediately after the second server-client record. The paired walk at 0x22f020 advances a server-client pointer by 0x1678 and a connection-state pointer by 0x2650. The comparison at 0x22f055 uses the server-client end pointer. In the tested branch, the connection-state field has offset 0x10 and the client record also contributes a field at 0x1210. The fixture supplies separate record buffers and an expanded end pointer directly to the loop body. The retail preamble still selects its original storage.

Treat the connection-table end address with care. At 0xcd35c and 0xd5487, instructions load that address and add an index scaled by 0x3218. At 0xd5491 the resulting pointer is dereferenced at offset 0x2010. These references access adjacent storage. Replacing every matching address with a new end pointer would redirect those accesses. The type and ownership of that adjacent storage remain unresolved.

The next engine dependency is the allocation, initialization and teardown path for each paired table, followed by the link from an admitted connection to a separately owned game entity. Validate every address consumer by behavior before enabling a running session. The separate lobby slot index supplies no evidence for either dependency.

Run tools/check_engine_routines.py with Python, pefile 2024.8.26, unicorn 2.1.4 and the path to the supported iw4sp.exe. It reads the retail image and executes bounded routines inside an emulator. It checks the actual bit helpers with two-bit widths, the unmodified two-record scan, and the paired loop body with four fixture records. The existing native codec checker covers the call-site changes on a private image.

## Client lifecycle on the supported Steam build

Level setup at 0x1716c5 supplies a count of two and clears 0x15fc0 bytes for two 0xafe0-byte player states. The loop at 0x171707 binds each entity's +0x108 field to its player state using the level count. The server setup at 0x22d05e separately clears 0x2cf0 bytes and limits its traversal to two at 0x22d11e. The callback at 0x22cf90 converts the server-record address back to a slot using the original table base, calls 0x15e350 with the slot and stores the entity address at server-record offset 0x1670. Moving the table requires updating this inverse mapping as well as forward lookups.

Per-player setup at 0x15e350 clears a player state and a separate 0x198-byte auxiliary record, preserving the latter's +0x178 field. It stores the player-state pointer at entity offset 0x108. The auxiliary array also requires independent storage analysis. Bulk reset at 0x231ac0 unlinks two entity pointers and requests a 12-byte clear per server record.

The emulator verifies selected instruction blocks. It supplies fixture data and models the reset helper's 12-byte clear. The observer samples only the two retail slots, with sequential reads every quarter second. Link flags describe pointer equality, not spawn or local input ownership. A single transitional sample can straddle a game update. Capture stable states before and after guest departure and compare the host and guest rows.

## Live two-player departure baseline

On November 15, 2026, the host and Knight joined a normal Steam Spec Ops session on the supported `iw4sp.exe`. The read-only observer captured 1,344 rows across two slots. At 30.062 seconds, both server-to-entity and entity-to-player pointer comparisons first became true. They remained true through 139.371 seconds. At the next sample, 139.635 seconds, both comparisons were false for both slots and both server-record state fields had cleared to zero. The host reported that Knight left and the game returned the host to the menu. The capture continued through 176.803 seconds with both links cleared. The original game therefore ended this session for both participants when the guest left. The trace does not establish whether an individual guest can be removed while a four-player host continues. The local raw CSV is in `specops4-dev/reports/lifecycle-live-knight-2026-11-15.csv` and is excluded from source control.

## Three-player storage audit

`tools/audit_player_storage.py` validates the installed executable hash and inventories exact direct RIP-relative references. It found 17 references to the server-client base and three to its two-record end, 12 references to the connection base and seven to its two-record end, 22 references to the player-state base pointer, and eight to the player count. It also found 485 references to the entity storage base. The instruction at 0x23281a writes through the address immediately after the two server-client records. The connection end address is likewise used as the base of adjacent indexed storage at 0xcd35c and 0xd5487. Extending either table in place would overwrite state that the executable accesses. These counts describe direct references only and cannot prove all pointer-derived uses have been found. The full local inventory is `specops4-dev/reports/player-storage-direct-refs.json`.

`tools/storage_relocation.py` validates the supported executable SHA-256 and constructs four-record private buffers for server clients, co-op connections, player states and auxiliary records. It copies the first two records and zeroes the added slots. Its patch plan contains 180 direct instruction changes and 24 whitelisted indexed-address changes (23 connection, one client). It checks exact original instruction bytes, displacement fields and signed 32-bit reach. End-address references used by neighboring data remain untouched. The bounded Unicorn tests exercise four-slot scans, setup and reset walks, entity binding, auxiliary initialization and indexed fourth-slot reads. Those tests do not establish network admission or a working three-player session.

`runtime/winmm.cpp` forwards 180 WinMM exports, verifies the exact executable hash and logs under `%LOCALAPPDATA%\OpsHub\SpecOps4\runtime.log`. Only a local `specops4.storage-test.enable` marker enables the memory patch. The runtime allocates four buffers near the game image, installs the 204 checked instruction patches and two auxiliary-read hooks, and refuses mismatched bytes. The isolated mapped-image checker verifies installation and rollback. In a local solo test, The Pit loaded and returned to the mission menu after the auxiliary teardown hook was corrected. The 24 indexed connection/client changes have passed isolated checks, but have not run in a live game yet. Session admission, per-player replication and game launch integration remain unfinished; do not distribute the test loader as a playable four-player mod.
